# 从首次接入到持续采集的流程

本文说明采集器如何在不开放数据库连接、只有一次基线导出与事务事件流的条件下，拿到与来源一致的正式库存。网关契约见 `source-contract.md`。

## 1. 首次接入（基线）

1. `GET /snapshot` 领取已提交基线，原始字节立即经 `Archive` 收存并写采集日志。
2. 按基线携带的 `relation`（id/epoch/fields）建立字段目录，按字段布局把每行物化为正式库存。
3. 本地游标定位到基线 `barrier`，状态原子落盘（临时文件 → fsync → 目录 fsync → rename）。
4. 向 `POST /confirm` 确认 `barrier`：基线本身就是已提交数据，barrier 是合法提交边界。

基线包含到 barrier 为止的数据，之后只领取 `lsn > barrier` 的事件，因此导出与续接之间没有间隙、也没有重叠——即使导出期间来源仍在写入，调整也会以事务事件形式在流中到达。

## 2. 持续采集（事务事件流）

每一轮 `/changes?after=<游标>` 按固定顺序处理，保证崩溃安全：

1. **先收原始资料**：整页字节写入 `Archive` 与 `journal.ndjson`（fsync）。
2. **再应用事件**：纯函数顺序处理，更新内存状态。
3. **再持久化检查点**：`state.json` 原子替换并 fsync。
4. **最后确认**：只对本页中已经完成第 3 步的 `commit` 位置调用 `/confirm`。

事件语义：

- `begin`：开启按 `tx` 隔离的暂存区。
- `row`：进入对应事务暂存区，**绝不直接改写正式库存**；按该事件 relation/epoch 的字段解释，缺失字段目录或值数量不符直接拒绝。
- `abort`：丢弃该事务全部暂存行。
- `commit`：把该事务暂存行按 lsn 顺序物化为正式库存，字段级合并（旧 epoch 的行不套用新布局，也不凭空补新列）。
- `relation`：登记新 epoch 的字段布局，对之后相同 epoch 的行生效。

页边界不是事务边界，事务还会交错；暂存区保存在检查点里，所以**长事务跨多次领取、跨进程重启都不会丢**，在它 commit 之前对应货号始终显示有未决事务。

## 3. 确认的是“可靠接收位置”，不是“最后见到的位置”

- 发往 `/confirm` 的只有 commit 边界 LSN（以及基线 barrier），任意 begin/row/abort 位置不是合法确认点。
- 确认在本地 fsync 之后才发出，因此来源确认过的位置一定已经安全落在本地。
- 确认单调不倒退；已经确认过的提交不会重复发送。
- 确认请求返回 409 时，采集器回查 `/status`：若来源侧确认位置已不低于该 LSN（典型于响应丢失但请求实际成功），按事实对齐本地；其它错误留给下一轮重试，已落盘的数据不受影响。

## 4. 崩溃与进程重启

启动时 `Collector.bootstrap()`：

1. 优先读取 `state.json` 检查点，从其中的游标继续。
2. 检查点缺失/损坏时，按 `journal.ndjson` 顺序回放 `objects` 中的原始快照与事件页，完整重建库存、未决事务、游标和确认位置。
3. 若没有任何采集历史，则重新走首次基线流程。

任何一步崩溃后，重放到的事件其 lsn 不大于游标会被幂等跳过；未确认的提交边界会在后续轮次补确认。结果是不丢事件、不重复物化、未提交/回滚数据永远不会转正。

## 5. 保留窗口过期（410）

来源不保证旧位置永久可用。`/changes` 返回 410 时，响应中的 `rebuild` 指向重建入口：

1. 记录过期事件与旧游标。
2. 重新领取基线（新 barrier、新 relation/epoch），重建字段目录与正式库存，重建计数加一。
3. 确认新 barrier，再从新屏障续接。

## 6. 运营追平判断

`collector.sku(sku)` 返回单个货号的追平视图，`collector.skuReport()` 返回全部货号：

- `record` / `appliedLsn`：当前正式记录与最后一次已提交变更位置。
- `openTransaction`：该货号是否仍被未决事务触及（未 commit/abort）。
- `confirmedLsn`：已被来源确认可靠接收的提交边界。
- `sourceHigh`：来源当前高水位。
- `caughtUp`：货号存在正式记录、没有未决事务、且可靠接收位置已到达来源高水位。

全局 `collector.describe()` 另外给出 `caughtUp`、未决事务数、重建次数等总览。只发生过回滚的货号不会被永久判定为未追平。
